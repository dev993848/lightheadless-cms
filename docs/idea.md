# Техническое задание на разработку Headless CMS на Go

## 1. Введение и цели проекта

### 1.1 Назначение системы
Разработать легковесную headless CMS систему на языке Go, предназначенную для сбора и управления заявками с лендингов, ведения новостной ленты и базовой настройки системы. Система должна обеспечивать прием данных с HTML-форм, их сохранение в базу данных SQLite, отображение в административной панели и опциональную отправку заявок в Битрикс24 через вебхук.

### 1.2 Целевая аудитория
- Владельцы лендингов и небольших сайтов
- Маркетологи и специалисты по лидогенерации
- Веб-разработчики, нуждающиеся в простой CMS для сбора заявок
- Администраторы сайтов, не имеющие технического бэкграунда

### 1.3 Основные цели
- Создать единый бинарный файл, не требующий установки дополнительного ПО
- Обеспечить простой и интуитивно понятный интерфейс администратора
- Реализовать базовый функционал сбора лидов без необходимости настройки сложной инфраструктуры
- Предоставить возможность интеграции с Битрикс24 для автоматической передачи лидов
- Обеспечить хранение и управление новостным контентом с поддержкой Markdown

## 2. Функциональные требования

### 2.1 Модуль сбора заявок (Leads)

#### 2.1.1 API эндпоинт для приема заявок
Система должна предоставлять публичный HTTP эндпоинт для приема данных из HTML-форм:
- **Метод:** POST
- **Путь:** `/api/leads`
- **Content-Type:** application/x-www-form-urlencoded и application/json
- **Параметры запроса:**
  - `name` (обязательное) — имя клиента, строка до 255 символов
  - `phone` (обязательное) — номер телефона, строка до 20 символов
  - `email` (опциональное) — адрес электронной почты, валидация формата
  - `comment` (опциональное) — комментарий или дополнительная информация, текст до 1000 символов

#### 2.1.2 Валидация данных
При приеме заявки система должна выполнять:
- Проверку наличия обязательных полей
- Валидацию формата email (если указан)
- Очистку и санитизацию текстовых полей для предотвращения XSS
- Ограничение длины полей в соответствии с требованиями базы данных

#### 2.1.3 Сохранение заявок
- Автоматическое сохранение каждой заявки в таблицу `leads`
- Присвоение уникального идентификатора
- Фиксация даты и времени создания (timestamp)
- Установка статуса "new" для всех новых заявок
- Сохранение всех полей, включая опциональные

### 2.2 Административная панель

#### 2.2.1 Аутентификация администратора
- Форма входа по логину (email) и паролю
- Хранение пароля в базе данных в зашифрованном виде (bcrypt)
- Сессионная аутентификация с использованием cookies
- Защита всех страниц административной панели от неавторизованного доступа
- Возможность выхода из системы (logout)

#### 2.2.2 Общие требования к интерфейсу
- Использование HTMX для динамического обновления контента без перезагрузки страницы
- Адаптивный дизайн, корректное отображение на desktop и mobile
- Единый шаблон с навигационным меню для всех разделов админки
- Подтверждение действий перед удалением объектов

#### 2.2.3 Раздел управления заявками (Leads)
- **Список заявок:**
  - Табличное отображение со столбцами: ID, Имя, Телефон, Email, Дата создания, Статус
  - Пагинация по 20-50 записей на странице
  - Сортировка по дате (по убыванию по умолчанию) и статусу
  - Фильтрация по статусу (new, sent, error)
  - Поиск по имени, телефону и email

- **Детальный просмотр заявки:**
  - Отображение всех полей заявки
  - Возможность изменения статуса вручную
  - Возможность удаления заявки
  - Отображение информации об отправке в Битрикс24 (дата, статус, ошибка)

- **Экспорт заявок:**
  - Возможность экспорта текущего списка в CSV формат
  - Экспорт всех полей заявки

#### 2.2.4 Раздел управления новостями (News)

- **Список новостей:**
  - Табличное отображение со столбцами: ID, Дата, Заголовок, Краткий анонс, Дата создания
  - Пагинация по 10-20 записей на странице
  - Сортировка по дате новости (по убыванию)
  - Поиск по заголовку и анонсу

- **Создание новости:**
  - Форма с полями:
    - Дата новости (выбор даты, обязательное)
    - Заголовок (текстовое поле, до 255 символов, обязательное)
    - Изображение (загрузка файла, опционально)
    - Анонс (textarea, до 500 символов, опционально)
    - Описание (textarea с поддержкой Markdown, опционально)
  - Загрузка изображений на сервер с автоматической генерацией уникального имени
  - Поддержка форматов изображений: JPEG, PNG, GIF, WebP
  - Ограничение размера изображения до 5 МБ

- **Редактирование новости:**
  - Возможность изменения всех полей существующей новости
  - Замена изображения с удалением старого файла
  - Предварительный просмотр Markdown-контента

- **Удаление новости:**
  - Удаление записи из базы данных
  - Удаление связанного файла изображения с сервера
  - Подтверждение удаления

#### 2.2.5 Раздел настроек (Settings)

- **Общие настройки:**
  - Название сайта (текстовое поле)
  - Email администратора (используется для входа)
  - Смена пароля администратора (с подтверждением)

- **Настройки интеграции с Битрикс24:**
  - URL вебхука Битрикс24 (текстовое поле)
  - Чекбокс "Включить отправку в Битрикс24"
  - Тестовая отправка для проверки работоспособности вебхука
  - Отображение статуса последней отправки

- **Сохранение настроек:**
  - Применение настроек без перезагрузки сервера
  - Валидация URL вебхука при сохранении

### 2.3 Интеграция с Битрикс24

#### 2.3.1 Отправка заявок в Битрикс24
- При получении новой заявки через публичный API, если включена опция отправки, система должна асинхронно отправлять данные в Битрикс24
- Формат данных для Битрикс24:
  - Имя клиента → поле NAME
  - Телефон → поле PHONE (в формате массива объектов)
  - Email → поле EMAIL (в формате массива объектов)
  - Комментарий → поле COMMENTS
  - Дополнительно: заголовок сделки (TITLE) формировать как "Заявка с сайта [дата]"

#### 2.3.2 Обработка ответа Битрикс24
- При успешной отправке обновлять статус заявки на "sent"
- При ошибке отправки обновлять статус на "error"
- Логировать ответ Битрикс24 для диагностики
- Не блокировать сохранение заявки при недоступности Битрикс24

#### 2.3.3 Повторная отправка
- Возможность вручную отправить заявку в Битрикс24 из административной панели
- Возможность массовой отправки заявок со статусом "error"

### 2.4 Публичные эндпоинты

#### 2.4.1 API для получения новостей
- **GET** `/api/news` — получение списка новостей с пагинацией
- **GET** `/api/news/{id}` — получение конкретной новости по ID
- Формат ответа: JSON
- Поддержка CORS для доступа с любых доменов (настраиваемо)

#### 2.4.2 Публичный доступ к загрузкам
- Статическая раздача файлов из директории uploads
- Путь: `/uploads/{filename}`
- MIME-типы определяются автоматически

## 3. Нефункциональные требования

### 3.1 Производительность
- Время ответа API для приема заявок не более 100 мс (без учета отправки в Битрикс24)
- Поддержка не менее 100 одновременных запросов на прием заявок
- Загрузка страниц админки не более 2 секунд

### 3.2 Безопасность
- Защита от SQL-инъекций (использование параметризованных запросов)
- Защита от XSS-атак (экранирование вывода)
- Защита от CSRF (использование CSRF-токенов для форм админки)
- Сессионные cookies с флагами HttpOnly и Secure
- Ограничение размера загружаемых файлов
- Проверка MIME-типа загружаемых изображений

### 3.3 Надежность
- Автоматическое восстановление после сбоев (graceful shutdown)
- Валидация конфигурации при запуске
- Логирование всех ошибок с указанием времени и контекста

### 3.4 Удобство использования
- Единый бинарный файл без внешних зависимостей
- Простой запуск: `./cms`
- Автоматическое создание базы данных и таблиц при первом запуске
- Понятные сообщения об ошибках

- **Язык:** Go 1.21+
- **База данных:** SQLite 3 (встраиваемая)

## 5. Требования к API

### 5.1 Публичный API для приема заявок
- **Эндпоинт:** POST /api/leads
- **Content-Type:** application/x-www-form-urlencoded
- **Успешный ответ:** HTTP 200, JSON `{"status": "success", "message": "Lead saved"}`
- **Ошибка валидации:** HTTP 400, JSON с описанием ошибок
- **Внутренняя ошибка:** HTTP 500, JSON с сообщением об ошибке

### 5.2 Публичный API для новостей
- **GET** /api/news?page=1&limit=10
  - Ответ: JSON с массивом новостей и метаинформацией о пагинации
- **GET** /api/news/{id}
  - Ответ: JSON с полной информацией о новости
  - При отсутствии: HTTP 404

### 5.3 Административные эндпоинты
Все административные эндпоинты защищены аутентификацией:
- GET /admin/ — дашборд
- GET /admin/leads — список заявок
- GET /admin/leads/{id} — детали заявки
- POST /admin/leads/{id}/resend — повторная отправка в Битрикс24
- DELETE /admin/leads/{id} — удаление заявки
- GET /admin/news — список новостей
- GET /admin/news/new — форма создания новости
- POST /admin/news — создание новости
- GET /admin/news/{id}/edit — форма редактирования
- PUT /admin/news/{id} — обновление новости
- DELETE /admin/news/{id} — удаление новости
- GET /admin/settings — страница настроек
- POST /admin/settings — сохранение настроек
- POST /admin/settings/test-bitrix — тестирование вебхука

## 6. Пользовательские сценарии

### 6.1 Сценарий 1: Получение новой заявки
1. Пользователь заполняет форму на лендинге и нажимает "Отправить"
2. Форма отправляет POST-запрос на `/api/leads` вашей CMS
3. Система валидирует данные и сохраняет заявку в базу
4. Если включена интеграция с Битрикс24, система асинхронно отправляет данные в Битрикс24
5. Пользователь получает сообщение об успешной отправке

### 6.2 Сценарий 2: Просмотр и обработка заявок
1. Администратор входит в админку по `/admin`
2. Переходит в раздел "Заявки"
3. Видит список всех заявок с сортировкой по дате
4. Нажимает на заявку для просмотра деталей
5. Изменяет статус заявки на "Обработано"

### 6.3 Сценарий 3: Создание новости
1. Администратор переходит в раздел "Новости"
2. Нажимает "Создать новость"
3. Заполняет дату, заголовок, загружает изображение
4. Вводит анонс и полное описание в Markdown
5. Нажимает "Сохранить"
6. Новость появляется в списке и доступна через API

### 6.4 Сценарий 4: Настройка интеграции с Битрикс24
1. Администратор переходит в раздел "Настройки"
2. Вводит URL вебхука Битрикс24
3. Нажимает "Проверить соединение" для тестовой отправки
4. При успешной проверке включает чекбокс "Отправлять заявки в Битрикс24"
5. Сохраняет настройки

## 7. Требования к развертыванию

### 7.1 Запуск приложения
- Приложение должно быть скомпилировано в один бинарный файл
- Поддержка аргументов командной строки:
  - `-port` — порт для HTTP-сервера (по умолчанию 8080)
  - `-db` — путь к файлу базы данных (по умолчанию ./cms.db)
  - `-upload` — путь к директории для загрузок (по умолчанию ./uploads)

### 7.2 Первый запуск
- Автоматическое создание файла базы данных при отсутствии
- Автоматическое создание всех таблиц
- Создание учетной записи администратора по умолчанию:
  - Email: admin@example.com
  - Пароль: admin123 (с требованием смены при первом входе)

### 7.3 Конфигурация
- Все настройки хранятся в базе данных
- Возможность переопределения через переменные окружения:
  - `CMS_PORT`
  - `CMS_DB_PATH`
  - `CMS_UPLOAD_PATH`

## 8. Ограничения и допущения

### 8.1 Ограничения
- Система не поддерживает многопользовательский режим (один администратор)
- Не предусмотрена поддержка MySQL или PostgreSQL (только SQLite)
- Не предусмотрена система резервного копирования (встроенными средствами)

### 8.2 Допущения
- Предполагается, что сервер работает в окружении с поддержкой файловой системы
- Загрузка изображений работает только через веб-интерфейс админки
- Отправка в Битрикс24 выполняется синхронно в фоновом режиме

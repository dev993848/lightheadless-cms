# Agent Rules — Правила работы агентов

> Эти правила обязательны для любого агента (AI или человека), работающего над LightHeadless CMS.
> Цель: поддерживать актуальность документации и статусов без ручного контроля.

---

## 1. Правило начала сессии

**Перед тем как начать работу, агент ОБЯЗАН:**

1. Прочитать `project/status.md` — понять текущее состояние проекта
2. Прочитать `project/overview.md` — освежить контекст если нужно
3. Если работаешь с API — прочитать `project/api.md`
4. Найти задачу в `status.md` в секции "В работе" или "Следующий шаг"

**Не начинай писать код без понимания текущего статуса.**

---

## 2. Правило обновления статуса

### Когда обновлять `project/status.md`

| Событие | Действие |
|---|---|
| Начал работу над задачей | Переместить задачу в "В работе", добавить дату |
| Завершил задачу | Переместить в "Выполнено", добавить дату и краткое описание |
| Нашёл проблему/блокер | Добавить в "Блокеры и проблемы" |
| Изменил архитектурное решение | Добавить в "Важные решения" + обновить architecture.md |
| Завершил этап разработки | Обновить "Прогресс по этапам" |

### Формат записи в "В работе"
```
- [x] Задача описание (Started: 2026-03-26)
```

### Формат записи в "Выполнено"
```
- [x] Задача описание (Done: 2026-03-26)
  - Заметки: что сделано, как, почему именно так
```

## 3. Правило документирования API

**Если ты изменил, добавил или удалил endpoint — обнови `project/api.md`.**

Обязательные поля для каждого endpoint:
- Метод и путь
- Описание
- Query/Path параметры (если есть)
- Request body (если есть) с типами
- Response — все возможные статусы и структуры
- Пример запроса и ответа
- Ошибки (400, 401, 404, 429, 500)

---

## 4. Правило документирования кода

Агент НЕ обязан писать комментарии к каждой функции, но обязан:

- Документировать **публичные интерфейсы** пакетов (exported types, functions)
- Добавлять комментарий если логика **неочевидна** (не "что делает", а "почему так")
- При сложном SQL-запросе — добавить комментарий с объяснением
- Не писать комментарии типа `// GetByID returns lead by id` — это шум

---

## 5. Правило тестов

**Каждый коммит с production кодом должен содержать тесты.**

Исключения (документировать в status.md):
- main.go (только инициализация)
- Шаблоны HTML (визуальная проверка)

Если тест невозможно написать прямо сейчас — добавить TODO в status.md:
```
- TODO: Написать тест для X (причина откладывания)
```

---

## 6. Правило архитектурных решений

Если агент принимает решение которое **отличается от architecture.md**:

1. Остановиться
2. Описать проблему и предложить альтернативу в status.md в секции "Блокеры и проблемы"
3. Дождаться подтверждения от разработчика
4. После подтверждения — обновить architecture.md

**Не менять архитектуру молча.**

---

## 7. Правило коммитов

Формат commit message:
```
<тип>: <краткое описание>

<детали если нужны>
```

Типы:
- `feat:` — новая функциональность
- `fix:` — исправление бага
- `test:` — добавление тестов
- `docs:` — обновление документации
- `refactor:` — рефакторинг без изменения поведения
- `chore:` — вспомогательные задачи (Makefile, CI)

Примеры:
```
feat: add IP rate limiting for POST /api/leads
fix: fix session expiry not checked on every request
test: add table-driven tests for lead validation
docs: update api.md with CSV export endpoint
```

---

## 8. Правило обновления MEMORY

При работе с Claude Code — сохранять важные решения и контекст в `~/.claude/projects/.../memory/`.

Что сохранять в memory:
- Принятые архитектурные решения с обоснованием
- Предпочтения разработчика по стилю кода
- Блокеры которые были решены нетривиальным способом

Что НЕ сохранять в memory (это в status.md):
- Текущий статус задач
- API документацию
- Структуру кода

---

## 9. Чеклист перед завершением задачи

Перед тем как сказать "готово":

```
[ ] Код компилируется: go build ./cmd/server
[ ] Тесты проходят: go test ./...
[ ] Race detector: go test -race ./...
[ ] status.md обновлён
[ ] api.md обновлён (если изменился API)
[ ] architecture.md обновлён (если изменилась архитектура)
[ ] Комментарии к неочевидной логике добавлены
```

---

## 10. Правило блокеров

Если агент столкнулся с блокером (неясность в требованиях, конфликт решений):

1. Не угадывать — описать блокер в status.md
2. Предложить 2-3 варианта с трейдоффами
3. Явно попросить решения

Формат в status.md:
```markdown
### Блокер: [Название]
**Проблема:** ...
**Варианты:**
- A: ... (плюсы/минусы)
- B: ... (плюсы/минусы)
**Рекомендую:** A, потому что ...
**Нужно:** решение от разработчика
```
